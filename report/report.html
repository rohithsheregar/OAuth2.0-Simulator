1. Introduction

OAuth 2.0 is an authorization framework. It lets a third-party application obtain limited access to a user’s data on another service without ever learning the user’s password. That separation is the reason OAuth replaced the older pattern of “give the app your username and password.”

This assignment implements a basic flow simulation of the most common grant: the Authorization Code Grant. All three protocol roles — Client, Authorization Server, and Resource Server — run locally in one Flask application. No Google or GitHub developer account is required.

The work has three parts required by the BCS703 assignment: (1) a working implementation with test cases, (2) a web-based virtual lab that visualizes the Authorization Code Grant flow, and (3) this technical report.

Scope of the simulation: in-memory dictionaries instead of a database, HTTP on localhost instead of HTTPS, and a single registered confidential client. The protocol decisions (short-lived codes, single-use codes, client authentication at the token endpoint, Bearer validation, state round-trip) are real.

2. Algorithm / Protocol Explanation

The Authorization Code Grant is a six-step algorithm involving three roles. The user-agent (browser) is the channel between the Client and the Authorization Server for login and consent. The Client later talks to the token endpoint and the Resource Server as a confidential party that holds a client_secret.

2.1 Roles

RoleResponsibility in this lab
Client (third-party app)Requests limited access. Never sees the user’s password. Exchanges a code for a token using its secret.
Authorization ServerAuthenticates the user, collects consent, issues a short-lived code, then issues an access token.
Resource ServerHolds protected profile data. Accepts only a valid, unexpired Bearer token.

2.2 Six-step algorithm

01
Client redirect. The Client redirects the browser to GET /authorize with response_type=code, client_id, redirect_uri, scope, and a random state.
02
User login. The Authorization Server authenticates the resource owner (simulated username/password). The Client does not receive the password.
03
Consent and code. If the user approves, the server stores a code (TTL ≈ 60 s, used=false) and redirects to redirect_uri?code=…&state=….
04
Code exchange. The Client POSTs to /token with grant_type=authorization_code, the code, redirect_uri, client_id, and client_secret.
05
Access token issued. After validation the server marks the code used and returns access_token, token_type=Bearer, expires_in, and scope.
06
Protected resource. The Client calls GET /resource with Authorization: Bearer <token>. A valid token yields mock profile JSON; otherwise HTTP 401.

2.3 Validation rules (the “algorithm” at each gate)

/authorize accepts the request only if response_type is code, the client_id is registered, the redirect_uri is on that client’s allow-list, and every requested scope is allowed.

/token rejects the exchange if the client secret is wrong, the code is unknown, the code is expired, the code was already used, or client_id / redirect_uri do not match the stored grant.

/resource rejects the call if the Authorization header is missing, the token is unknown, or the token TTL has elapsed.

The state value is generated by the Client and must come back unchanged on the callback. A mismatch means the callback is not bound to the browser session that started the flow (CSRF).

4. Virtual Lab Design

The assignment requires a web-based virtual lab so the Authorization Code Grant can be visualized, not only described. The page at /lab is that instrument: the six-step flow stays on screen, the user supplies inputs, and each hop shows its request and response.

  • Horizontal workflow (steps 1–6). The active step is highlighted; completed steps turn green.
  • Sequence diagram. Client, Authorization Server, and Resource Server sit on three lanes. The live arrow and travelling packet show who is talking to whom.
  • Request / response board. Each stage fills two panes on the same screen: outbound JSON on the left, inbound JSON on the right. The guided demo stays on this board so the operator does not have to scroll to a log to understand the exchange.
  • Stage pills. After several steps, previous packets can be recalled without leaving the board.
  • Editable inputs. Scope, username/password, and client secret can be changed to provoke rejection.
  • Guided demo. Runs the happy path, pauses on each pair of panes, and hides the page chrome so the protocol stays in view.
  • Seven security experiments. Invalid secret, expired code, replayed code, bad redirect URI, invalid token, expired token, and state round-trip — each writes into the same board.

Run locally with python app.py, then open http://127.0.0.1:5000/lab. Use Play flow for a walkthrough, or click each button by hand.

5. Experimental Results

Correctness was demonstrated with python test_flow.py against the running server, and the same cases can be repeated from the virtual lab. Observed outcomes:

Test 1 — Happy path

Input: client client_abc123, user alice, scope read:profile read:email, valid secret.
Output: code issued, token issued, GET /resource returns HTTP 200 with user=alice and email=alice@example.com. PASS 

{
  "user": "alice",
  "name": "Alice Smith",
  "email": "alice@example.com",
  "scope": "read:profile read:email",
  "message": "Access granted to protected resource"
}

Test 2 — Invalid client credentials

Input: same code, client_secret=WRONG_SECRET at /token.
Output: HTTP 401, {"error": "invalid_client_credentials"}. The code remains unused. PASS

Test 3 — Expired authorization code

Input: a freshly issued code whose expires_at is forced into the past (lab control /client/test/expire_code, equivalent to waiting beyond the 60 s TTL).
Output: HTTP 400, {"error": "code_expired"}. PASS

Test 4 — Reused authorization code (replay)

Input: first /token with a valid code succeeds; the identical code is posted again.
Output: first call HTTP 200; second call HTTP 400, {"error": "code_already_used"} (lab wording notes replay). PASS

Test 5 — Mismatched redirect_uri

Input: GET /authorize with redirect_uri=http://evil.com/steal (not in the client’s registered list).
Output: HTTP 400, {"error": "invalid_redirect_uri"}. No login page is shown. PASS

Test 6 — Invalid or expired access token

Input A: Authorization: Bearer totally_fake_token → HTTP 401, invalid_token.
Input B: a real token whose TTL is forced to the past → HTTP 401, token_expired. PASS

Test 7 — state parameter round-trip

Input: state=csrf_guard_12345 on the authorize request.
Output: the callback returns the same string. The Client can accept the code only if it matches the value stored for this browser session. PASS

Together these seven cases show both functional correctness (the protected resource is reachable) and the negative paths the assignment asks us to demonstrate.

6. Security Considerations

  • state prevents CSRF. An attacker who tricks the victim’s browser into finishing a different authorization cannot satisfy a Client that checks the returned state against the value it generated.
  • Codes are short-lived and single-use. A leaked code expires in about one minute and cannot be exchanged twice. That closes the classic authorization-code replay window.
  • The client secret never belongs in the browser in production. Token exchange is a confidential-client operation. This lab performs it from Flask for teaching; a public SPA would need PKCE.
  • Tokens are Bearer credentials. Anyone who holds the token can call the API. They must travel only on encrypted channels (HTTPS / TLS). This localhost demo uses HTTP on purpose and must not be copied to a public network as-is.
  • redirect_uri allow-listing stops the Authorization Server from delivering a code to an attacker-controlled callback.
  • Passwords stay on the Authorization Server. That is the core privacy property of OAuth compared with sharing account credentials with every third-party app.

7. Conclusion

We implemented the OAuth 2.0 Authorization Code Grant as a complete local simulation: registered client, user login, consent, authorization code, access token, and protected resource. Automated tests and the virtual lab both show that the happy path returns profile data and that invalid secrets, expired or reused codes, unregistered redirect URIs, and bad or expired tokens are rejected.

Building the virtual lab around the six-step flow and a side-by-side request/response board made the protocol observable. Each stage is no longer a black box that ends in a success banner; the JSON that actually moved between Client, Authorization Server, and Resource Server remains on screen.

Limitations versus production OAuth 2.0 are deliberate and should be stated: no TLS, no persistent store, plaintext demo passwords, no PKCE, no refresh-token rotation, no token revocation list, and a single Flask process instead of separately deployed servers. Those would be the next engineering steps if this teaching model were hardened for a real identity platform.

What we learned: OAuth is not encryption of the user’s password. It is a carefully ordered authorization protocol whose safety depends on TTL, single-use codes, authenticating the Client at the token endpoint, binding the callback with state, and treating access tokens as secrets.
